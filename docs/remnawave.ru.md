# Remnawave: панель, VPN-нода и подписки на одной VPS

[🇺🇸 English](remnawave.md) · [🇷🇺 Русский](remnawave.ru.md) · [К README](../README.ru.md)

[Быстрый старт](#быстрый-старт) · [Домен подписок](#отдельный-домен-подписок-необязательно) · [Устройство установки](#как-устроена-установка) · [Настройки](#повторный-запуск-и-управление-настройками) · [Диагностика](#проверки-и-диагностика) · [Резервные копии](#обновление-и-резервные-копии) · [Удаление](#удаление) · [Для разработчика](#проверки-разработчика)

Этот режим устанавливает Remnawave Panel, локальную Remnawave Node с Xray,
PostgreSQL, Valkey и Nginx через Docker Compose. После установки создайте
пользователя в группе **VPN Users** и скопируйте его персональную ссылку подписки.
В подписку попадут VLESS Reality и Hysteria2, если оба протокола включены.

Существующий режим `standalone` продолжает устанавливать sing-box. Автоматическая
миграция работающего sing-box в Remnawave не выполняется. Для первой установки
Remnawave нужна чистая Ubuntu 22.04, 24.04 или 26.04, архитектура amd64/arm64,
Python 3 и Docker Engine 28+ с Compose v2. При отсутствии Docker установщик
ставит Ubuntu-пакеты `docker.io` и `docker-compose-v2`. Если установлен старый
Docker или отсутствует Compose, скрипт сообщает об этом до запуска панели.

Для совместного размещения панели и ноды разумный начальный ориентир — 4 ГБ RAM;
реальные требования зависят от числа пользователей и трафика.
[Требования Remnawave](https://docs.rw/install/requirements/).

## Быстрый старт

Все команды ниже выполняются из каталога репозитория на VPS.

1. Создайте DNS **A**-запись `panel.example.com`, направленную на публичный IPv4 VPS.
   Используйте DNS-only, без CDN-проксирования. Этот режим публикует только IPv4;
   не добавляйте AAAA-записи для доменов панели и Hysteria2.
2. Разрешите входящие порты в firewall провайдера:
   `80/tcp`, `8443/tcp`, `443/tcp` для VLESS и `443/udp` для Hysteria2.
   Существующий SSH-порт должен оставаться доступным.
3. Подготовьте конфигурацию и установите:

```bash
cp .env.remnawave.example .env
nano .env
sudo bash install.sh
```

Задайте `PANEL_DOMAIN`, `LETSENCRYPT_EMAIL`, `REALITY_SERVER_NAME` и
`HYSTERIA_MASQUERADE_URL`. За NAT облачного провайдера обязательно задайте
`SERVER_IPV4` — публичный IPv4, а не приватный адрес интерфейса.
Если нужен только VLESS, установите `ENABLE_HYSTERIA=false`; параметры Hysteria2
тогда не нужны. Пустой `HYSTERIA_DOMAIN` использует домен панели.

Начальные административные данные находятся в файле с правами `0600`:

```bash
sudo cat /opt/proxy-bootstrap/remnawave/credentials.txt
```

Откройте `https://panel.example.com:8443`, войдите и создайте пользователя:
задайте срок действия, нужные лимиты и группу **VPN Users**. Скопируйте его
подписочную ссылку из панели и импортируйте в совместимый VPN-клиент. В дальнейшем
клиент получает изменения при обновлении подписки. Подписочная ссылка содержит
секрет доступа; её нельзя публиковать. Это конфигурационная подписка, без биллинга.

### Совместимость клиентов VLESS

Закреплённое ядро Xray по умолчанию принимает Reality-клиентов, объявляющих версию
`26.3.27` или новее. Некоторые клиенты на sing-box, включая Hiddify, объявляют
`1.8.1` и получают отказ даже с правильными ключами из подписки. Для таких
клиентов явно включите совместимость до установки:

```env
REALITY_MIN_CLIENT_VERSION=1.8.1
```

По умолчанию используется `26.3.27`. Xray предупреждает, что снижение порога
повышает риск обнаружения и блокировки IP; выбирайте его, только если нужна
такая совместимость. См. [реализацию закреплённой версии Xray](https://github.com/XTLS/Xray-core/blob/v26.7.28/infra/conf/transport_security.go).
На существующей установке измените
`streamSettings.realitySettings.minClientVer` у VLESS inbound в конфигурационном
профиле панели. Изменение `.env` не перезаписывает существующий профиль. Этот
параметр не влияет на Hysteria2 и не гарантирует поддержку всех версий клиентов.

## Отдельный домен подписок (необязательно)

По умолчанию подписочные ссылки используют домен панели:
`https://panel.example.com:8443/api/sub/<token>`. Для отдельного домена задайте
в `.env` **до первой установки**:

```env
PANEL_DOMAIN=panel.example.com
SUBSCRIPTION_DOMAIN=sub.example.com
PANEL_HTTPS_PORT=8443
```

Создайте DNS-only **A**-запись `sub.example.com` на публичный IPv4 той же VPS,
без CDN-проксирования и AAAA-записи. Скрипт проверит DNS и включит домен
в управляемый сертификат Let's Encrypt. Дополнительные сервер и порт не нужны:
оба домена используют `PANEL_HTTPS_PORT`. Порт `443/tcp` по умолчанию остаётся
за VLESS.

Панель остаётся на `https://panel.example.com:8443`, а выдаваемые подписочные
ссылки используют `https://sub.example.com:8443/api/sub/<token>`.
На домене подписок Nginx пропускает только GET/HEAD-запросы подписки по `/api/sub/`;
страницы панели и административный API возвращают `404`.
Подписки также остаются доступны через домен панели.

Оставьте `SUBSCRIPTION_DOMAIN` пустым, не задавайте его или укажите `PANEL_DOMAIN`,
чтобы сохранить исходную схему с одним доменом. Существующие состояния установки
без нового параметра сохраняют адреса подписок. Автоматическая смена доменов уже
установленной системы не реализована; изменение `.env` не переносит старые ссылки.

## Как устроена установка

| Назначение | Публикуемый порт |
| --- | --- |
| Панель и подписки через HTTPS (один или два домена) | `8443/tcp` |
| VLESS Reality | `443/tcp` |
| Hysteria2 | `443/udp` |
| Certbot standalone для ACME | `80/tcp` во время выпуска/продления |
| API панели для обслуживания | `127.0.0.1:3000`, только loopback |
| API ноды, PostgreSQL, Valkey | не публикуются на хосте |

Панель и нода связаны через закрытый порт в Docker bridge-сети. Внутренний адрес
ноды в панели — `node:2222`. Внешние адреса подключения находятся в разделе Hosts.
Вариант с bridge выбран для совместного размещения: функции ноды, требующие
доступа к firewall/сетевому пространству самого хоста, не настраиваются.

Установщик создаёт администратора до запуска публичного Nginx, генерирует ключи,
через API создаёт профиль, ноду, группу и Hosts. Начальный профиль блокирует
проксирование в приватные сети. У каждой учётной записи свои VPN-учётные данные.

Docker сам публикует VPN- и HTTPS-порты, и обычные правила UFW не фильтруют эти
публикации. `FIREWALL_BACKEND` здесь управляет доступом к хостовому TCP/80 для ACME.
Ограничения по IP для панели/пользователей задавайте в firewall провайдера либо
осознанно через правила Docker. Установщик не сбрасывает firewall и не меняет SSH.

Поддерживаются Hysteria2 masquerade и необязательный `salamander`. `gecko` явно
отклоняется: совместимость его подписок этим режимом не гарантируется. Параметры
одного пользователя `VLESS_UUID`, `HYSTERIA_PASSWORD` и заранее заданные ключи из
standalone-конфигурации также отклоняются; используйте новый пример `.env`.

## Повторный запуск и управление настройками

Состояние и секреты сохраняются в `/opt/proxy-bootstrap/remnawave/state.json`.
Секреты, состав группы и UUID объектов не пересоздаются при повторном запуске.
После завершения bootstrap скрипт не перезаписывает профили, Hosts и пользователей
из панели. Удалённые в панели объекты не восстанавливаются молча.

Повторный `install.sh` возобновляет прерванную установку. Его инфраструктурные
параметры должны совпадать с первоначальными. Меняйте пользователей, лимиты и
маршрутизацию через панель. Изменение портов требует также изменения Docker
публикаций и firewall; автоматическая смена портов/доменов текущей версией не
реализована. Не удаляйте `state.json`, пытаясь применить новый `.env`.

## Проверки и диагностика

```bash
sudo bash scripts/healthcheck.sh
sudo bash scripts/remnawave.sh smoke-test
sudo bash scripts/remnawave.sh smoke-test --external
sudo docker compose --project-directory /opt/proxy-bootstrap/remnawave \
  -f /opt/proxy-bootstrap/remnawave/compose.json logs --tail 100 panel node nginx
```

Обычный healthcheck проверяет контейнеры, HTTPS панели, завершение регистрации
администратора и работающую ноду/Xray. Smoke-test создаёт временного пользователя
на 15 минут с лимитом 100 МБ, получает настоящую JSON-подписку через HTTPS
настроенного домена подписок, запускает временный Xray-клиент и выполняет HTTPS-запрос через каждый включённый
протокол. По завершении пользователь удаляется. После обрыва процесса очистка
выполняется при следующем запуске smoke-test.

При отдельном домене подписок healthcheck также проверяет его HTTPS и убеждается,
что через него недоступны страницы панели и API аутентификации.

По умолчанию тест подключается к ноде внутри Docker-сети, сохраняя ключи и TLS
параметры из подписки. `--external` использует публичные адреса из подписки,
но запрос по-прежнему исходит с VPS и зависит от поддержки NAT loopback.
Проверка с внешнего устройства необходима для подтверждения доступности портов
у провайдера. Ошибки тестового клиента сохраняются в закрытый `last-probe.log`
в каталоге установки. Тестовый пользователь и контейнер не предназначены для
постоянного использования.

Если клиент подключается, но сайты не открываются, проверьте VLESS и Hysteria2
по отдельности вместо автоматического выбора, затем сравните Wi-Fi и мобильную
сеть. Успешный smoke-test на Xray не проверяет ядро, DNS и маршрутизацию мобильного
клиента. Docker-сеть этого установщика не имеет выхода по IPv6. Используйте
IPv4-only DNS/маршрутизацию в клиенте либо настройте и проверьте IPv6 в Docker-сети,
прежде чем отправлять IPv6-адреса через VPN. Наличие IPv6 на самом VPS не даёт
IPv6-связности контейнеру ноды.

`CERTBOT_STAGING=true` выпускает тестовый сертификат. Только в этом режиме
проверки HTTPS панели и подписок отключают проверку доверия к сертификату, а тестовый
VPN-клиент закрепляет SHA-256 тестового сертификата. Обычные клиенты
таким сертификатам не доверяют; для рабочей установки используйте `false`.

## Обновление и резервные копии

```bash
sudo bash scripts/remnawave.sh backup
sudo bash update.sh
```

`update.sh` сначала создаёт согласованный `pg_dump` базы и копию состояния,
конфигурации, сертификатов и runtime, затем применяет закреплённые в коде версии
и выполняет проверки. Он не выбирает произвольный `latest` и не переписывает
профили через API. Для обновления версии сначала обновите репозиторий до варианта
с проверенным набором образов.

Копии находятся в `/var/backups/proxy-bootstrap/remnawave/`. Они включают секреты:
храните их закрыто и копируйте за пределы VPS. Перед восстановлением проверяются
SHA-256 файлов и читаемость дампа PostgreSQL. Восстановление заменяет текущую БД
и конфигурацию; перед заменой создаётся дополнительная резервная копия.

```bash
sudo bash scripts/remnawave.sh restore \
  /var/backups/proxy-bootstrap/remnawave/ИМЯ_КОПИИ
```

Восстанавливаются также версии образов и runtime из копии. Это важно при
изменении схемы БД: откат только Docker-образа недостаточен. Сценарий рассчитан
на восстановление той же конфигурации IP/доменов, а не на автоматическую миграцию
на другой адрес. Сертификат обновляется через certbot при необходимости.

Продление сертификатов выполняет `certbot.timer`. Deploy-hook обновляет PEM-файлы,
перезагружает Nginx и просит панель перезапустить ноду с актуальным сертификатом.
Для этого используются копии скриптов внутри каталога установки; наличие
исходного checkout репозитория не требуется.

## Удаление

```bash
sudo bash uninstall.sh
# Полная очистка управляемых данных, также с резервной копией перед удалением:
sudo bash uninstall.sh --purge
```

Обычное удаление останавливает и удаляет контейнеры, но сохраняет том БД,
конфигурацию и секреты. Повторная установка возобновляет работу. `--purge` удаляет
также эти данные. Резервные копии, Docker и сертификаты Let's Encrypt сохраняются.

## Проверки разработчика

```bash
python3 -m unittest discover -s tests -v
for script in install.sh update.sh uninstall.sh scripts/*.sh templates/*.sh.tpl; do
  bash -n "$script" || exit 1
done
python3 tests/integration_remnawave.py
python3 tests/integration_remnawave.py --separate-subscription-domain
```

Последние две команды проверяют общий и отдельный домен подписок соответственно.
Запускайте их по очереди: они используют одно имя Compose-проекта.
Каждая команда запускает реальные закреплённые контейнеры с тестовым
сертификатом и портами только на loopback. Нужны Docker, Compose, OpenSSL,
доступ к registry и интернету. Тест отказывается работать, если уже существует
Compose-проект с тем же именем; после проверки удаляет свои контейнеры и тома.
Он не устанавливает пакеты, не меняет host firewall и не запускает certbot.
Проверяются также реальное восстановление дампа PostgreSQL, сохранение ссылок
подписки и правок профиля, а также перезагрузка Nginx/ноды при смене сертификата.
Прогон с отдельным доменом проверяет его наличие в сертификате, GET/HEAD-запросы
подписки и недоступность панели/API через домен подписок.

Проверка полной установки на чистой Ubuntu VPS, продления Let's Encrypt и
подключения из внешней сети выполняется отдельно.
